# 降噪与扫描决策表（decisions）

本文是 Phase 2/Phase 3 的决策依据。原则：**从响应判断资产是否真在跑、跑的是什么、跑得活不活**，而不是看端口通不通、域名解不解析。

## 1. 404 分类表（判断"404 是谁返回的"）

扫到 404 默认扔掉是最大浪费。不同来源的 404 信息量天差地别，处置方式完全不同：

| 404 来源 | 特征 | 含义 | 下一步打法 |
|---|---|---|---|
| Web 服务器原生 | Nginx 默认页、Tomcat 默认页、Apache 默认页 | 裸的、没配好路由的中间件 | 打中间件：默认口令、管理端点、解析漏洞 |
| 应用框架 | Spring Whitelabel、Django debug 404、Next.js 404 页 | 应用活着、路径不存在，框架信息白送，常带堆栈/路径/环境变量 | 挖应用：确认框架版本 → 框架已知洞；读报错细节找信息泄露 |
| 网关 | Kong 的 message、APISIX `{"error_msg":"404 Route Not Found"}` | 这是网关，路由表里没这个 path | 打网关管理面、枚举其他路由、找后端 service 列表 |
| CDN/WAF | 云厂商定制 404 页 | 域名挂 CDN/WAF 后面，真实源站未找到 | 找真实源站（历史 DNS、证书、IP 段交叉） |
| 软 404 | 状态码 200，内容却是"页面不存在" | 最骗人，必须靠内容 hash/长度判断 | 用响应长度、内容指纹、hash 聚类判断，不能只看状态码 |

## 2. 存活分级（"存活"不是布尔值，是程度）

| 档位 | 现象 | 含义 | 攻击优先级 |
|---|---|---|---|
| 端口通、应用没起 | TCP 握手成功、HTTP 无响应或连接重置 | 中间件在、应用挂了/没部署 | **最值得打**：直接打中间件层（默认口令/未授权重灾区） |
| 应用起、业务空 | 首页能开、接口全 401/403/500 | 鉴权挡着或后端依赖挂了 | 高价值：绕鉴权、找未授权端点 |
| 正常响应业务 | 首页+接口正常 | 活系统 | 按正常流程继续展开 |

## 3. 403/404 该不该扫（扫描模型判断）

扫描本质是信息探测：发不同输入（路径），看输出（响应）有没有差异。**响应有差异 = 路径有区分度 = 扫描有效**；某一层把所有输入抹平成同一输出，扫一万个路径和扫零个获得的信息一样多。

### 3.1 先做探针（扫描前必做，成本 10 秒）

发 5~10 个明显不存在的随机路径（如 `/asdfqwertasdf12345`）：

- **全部字节级一致** → 拦截层在内容层之前，扫描结果可信 → 放心扫。
- **不一致** → 存在软 404 或动态处理 → 扫描结果必须用内容指纹二次过滤。
- **全部 403 且完全一致** → WAF/鉴权统一拦截 → 别扫路径，转旁路或先打拦截层本身。

### 3.2 403 判断（看是谁挡的）

| 来源 | 特征 | 结论 | 该做什么 |
|---|---|---|---|
| WAF/统一访问控制层 | 所有路径一律 403、响应字节级一致 | 路径扫描纯浪费 | 换 IP、降速率、分块绕 WAF；或放弃此入口走旁路（其他子域名/端口/客户端直连/历史 IP） |
| 应用鉴权 | 路径真实存在，响应有区分度（已认证但权限不足 / 未登录访问需登录资源） | 扫能发现路径但发现了一样 403 | 转找未授权可访问的同源接口、鉴权绕过（PUT/DELETE/PATCH 方法切换、大小写、末尾加点加斜杠）、找该资源的其他访问方式 |
| 反代/路由层 | 路由规则明确禁止 | 扫描无效 | 找网关管理面拿全量路由、改 Host/SNI 试虚拟主机 |

### 3.3 404 判断

| 情况 | 结论 |
|---|---|
| 全局统一 404（所有不存在路径返回字节级完全相同的 404 页） | **扫描的理想情况**，响应有任何差异就等于路径存在，放心扫 |
| 软 404 | 用响应长度、内容指纹、hash 聚类判断，不能只看状态码 |
| 网关 404 | 对这域名扫路径意义不大，但网关本身是目标：扫网关管理面和其他路由对应的域名 |

### 3.4 硬封锁判断

全端口都 403、所有 Host 头都 403、所有路径都 403、响应还完全一致 → 前面是一层硬 WAF/硬鉴权，入口彻底封死，继续耗是负收益。

正确做法：**标记为硬封锁**，把精力转到该资产的其他入口——一个后端不会只有一个入口，封死一个不代表全封死。

## 4. 去重聚类（几千条 → 几十个真实系统）

按 IP/域名去重没意义（几千条里大量是同一套应用的不同入口），必须按指纹：

- favicon hash（SaaS 和内部系统爱用默认 favicon，hash 一致就是同一套）
- 页面标题和 meta
- 特定静态资源路径
- HTTP 响应头组合
- 报错页特征

指纹一致的聚成一类，一类只深挖一个代表，其余标记同源。

## 5. 响应特征 → 行动 速查

| 你看到什么 | 意味着什么 | 做什么 |
|---|---|---|
| Nginx 默认 404 页 | 裸中间件 | 打默认口令/管理端点/解析漏洞 |
| Spring Whitelabel | 应用活着，框架白送 | 查框架 CVE + 读报错堆栈 |
| 全部路径 403 且字节一致 | 硬 WAF/鉴权 | 转旁路，标记硬封锁 |
| 响应有差异的 404 | 路径存在信号 | 放心扫 |
| 状态码 200 但内容"不存在" | 软 404 | 内容 hash 过滤 |
| 端口开、HTTP 重置 | 中间件在、应用没起 | 打中间件层 |
| 首页开、接口全 401 | 鉴权挡着 | 绕鉴权/找未授权端点 |
