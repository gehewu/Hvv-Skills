# 关联编排（correlation）

Phase 5 依据。发现之后，把孤立信息点关联起来才能看出完整攻击面。每个资产在多个维度上与其他资产、其他信息关联。

## 1. 关联维度

| 维度 | 信号 | 背后含义 | 用途 |
|---|---|---|---|
| 代码同源 | 同前端框架、同网关、同部署模板 | 同一开发团队、同一安全基线、往往同一套漏洞 | 横向铺开 |
| 网络同段 | 同 IP 段 | 同机房、同 VPC，内网互通 | 纵向深入 |
| 证书同源 | 多张证书同一申请主体/邮箱 | 同一所有者 | 纵向深入 |
| 解析同 IP | 多域名解析到同一 IP | 同一台机器，拿下其中一个其他都暴露 | 纵向深入 |
| 供应链同指纹 | 自研框架、自研网关、同 favicon hash、同第三方组件 | 同一资产族 | 横向铺开 |
| 人员同源 | 多系统开发运维是同一批人 | 同一套密码习惯、配置习惯 | 攻击习惯复用 |

指纹类关联（代码同源、响应同指纹、供应链同指纹）是**横向铺开**的关键；网络和证书类关联（网络同段、证书同源、解析同 IP）是**纵向深入**的依据。

## 2. 攻击路径推演范式（信号 → 行动）

| 你发现 | 推演路径 |
|---|---|
| 边缘资产 A 与核心系统 B 解析到同一 IP | 打 A（老系统没人维护）→ 同机器提权 → 横向到 B |
| 测试环境 T 与正式环境 P 同证书、同前端指纹、代码同源 | 先在 T 上测试（没 WAF、随便测）→ 再去 P 上打 |
| 三个子系统同 favicon、同自研框架 | 指纹打通 → 在最弱的那个找到入口 → 另外两个同框架同洞 |
| 某资产解析的内网 IP 在另一资产的 JS 里也被请求过 | 内网拓扑片段拼接 |
| 前端暴露了测试环境地址 + 测试环境鉴权弱 | 拿下测试环境（与生产同代码）→ 生产一样有洞 |
| 鉴权白名单里有不该公开的接口 | 直接打，绕过登录态 |
| 错误码字典有"管理员专属"错误码 | 反推有管理员功能 → 找功能入口 |
| 第三方 SDK 回调地址可控 | SSRF 或开放重定向 |
| 老版本接口与新版并存（/v1/ /v2/ /v3/） | 旧接口鉴权/校验旧 → 已知绕过或已知漏洞 |
| 证书 SAN 列了内部域名 | 下一批要收集的资产 |
| 一个报错栈里的包名 | 反推后端自研代码结构 |
| 被动 DNS 里半年前的内网 IP | 现在可能还开着 |

## 3. 收尾习惯

**每次拿到一个响应，都问自己一句：它还告诉了我什么没注意到的。**

- 404 是谁返回的 → 决定打中间件还是挖应用
- 403 是哪一层拦的 → 决定继续扫还是转旁路
- 证书 SAN 列了哪些内部域名 → 下一批要找的资产
- 一段 JS 里残留的 API 和测试环境地址 → 现成的端点清单
- favicon 一样、响应头一样的两个系统 → 大概率同一套部署，打穿一个等于打穿全部
- 报错栈里的包名 → 反推后端自研代码结构
- 被动 DNS 记录里那个半年前的内网 IP → 现在可能还开着

把这些信号串起来，而不是扫完就过，是整件事的关键。三件套人人会用，但三件套之外还有大量展开空间，重点都在后面——种子给你了，怎么种出一片攻击面，看你怎么连。
